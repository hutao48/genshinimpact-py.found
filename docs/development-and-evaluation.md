# 原神乐器演奏检测器 · 开发与评测记录

[返回项目首页](../README.md)

这份文档保留了原 README 中的版本演进、检测原理与历史评测，供排查问题和参与开发时参考。项目名称为「原神乐器演奏检测器」，源码标识与构建产物使用 GenshinInstrumentDetector。

**阅读提示：**下列数值沿用原 README 的历史记录，反映对应版本在当时样本上的表现；本次文档整理没有重新运行这些评测。不同版本、乐器、曲目与采集环境的结果不能直接混用，也不能当作对任意演奏的准确率承诺。

## 版本演进

- Windows 1.0.8：镜花之琴召回 46% → 57%、晚风圆号召回 39% → 55%（圆号改用后备判定）、谐律键琴召回 62%–68% → 65%–70%；7 段录像合计 F1 67.1 → 68.4（精确率 73.5% → 72.1%，召回 61.7% → 65.1%）。
- Windows 1.0.7：镜花之琴、晚风圆号、谐律键琴按音色模板认键——镜花之琴精确率 10% → 58%、召回 10% → 46%，圆号 29% → 46% / 33% → 39%，谐律键琴 66%–78% → 71%–84%；圆号按键时长误差中位 323 → 231 ms（对照 7 段游戏录像）。
- Windows 1.0.6：快段落漏检明显减少——距上一次按键不到 0.2 秒的按键漏检率从 58% 降到 43%，总召回率 48% → 58%，精确率不降（对照 7 段游戏录像里的真实按键）。
- Windows 1.0.5（含未发布的 1.0.4）：BPM 改为按拍子显示（弹得更密时读数不再翻倍、突然升高）；修复谐律键琴、跃律琴的谐波被当成多按的键（对照游戏录像里的真实按键，多检减少 55%–70%）；修复移调被加了两次（+12 实际移了 +24）；边界值排查新增"节拍网格"（MIDI 量化的节奏）与"圆号按键时长"两项，谐波强的乐器不再误报"超出人手极限"。
- Windows 1.0.3：修复演奏停顿后轻微背景声被当成新按键；新按键门限从已确认的起音学习，停顿时保持。琴键显示改为最后一帧的当前状态，避免一批音频内已经结束的键仍高亮。大幅降低播放音量后，可停止并重新开始监听以重新学习电平。
- 1.0.2：新增**边界值排查**（同时按下超过 10 个键、很长一段间隔完全一致的连续音，作为判断是否使用脚本的证据）；BPM 跟随变速——变速后约 1–1.5 s 跟上（旧版速度常变时可以十几秒不动），连续快速连音的读数不再卡在 300 以下；界面改为深色卡片式，BPM 图纵轴自动缩放、可切换显示范围、悬停看读数，记录保留更久（BPM 4 小时、时长表 20000 条）并可导出 CSV。
- 1.0.1：游戏里有底噪、音效、背景音乐时，按键时长不再被频繁切断、拆成碎片或误报“松键/截止”。
- 1.0.0：BPM 与每个音的时长检测重写（起音对齐到敲击瞬间、同键连按逐个拆开、结束方式标注、和弦合并的 BPM 估计）；新增 Windows 安装程序与离线分析（`--analyze 录音.wav`）。

## 检测原理与历史评测

- 采集：WASAPI 回环/麦克风双模式，48 kHz、2048 采样/块；**所有时间戳取音频样本时钟**（实时与离线结果一致，不受读块抖动影响）。
- 检测：FFT（4096 + 16384 零填充）提取基频与谐波结构，逐键跟踪；攻击门限 + 谐波结构校验剔除背景杂音；连续 4 帧确认。
- 起音：1024 窗 / 256 帧移的 log 谱通量（SuperFlux 式）定位敲击瞬间；新音必须对应一个起音峰；硬截止"咔哒"（其后总功率下降）不算起音；与更强音同时出现、弱 6 dB 以上且 0.25 s 内消失的"起音旁瓣"剔除。
- 时长：按该音自身电平轨迹定位结束——急速截止取 -6 dB 半幅点并按截止陡峭度查表扣除释放尾音；同键重按（起音前后整窗电平回到"刚按下"水平）在新起音处结束；否则为余音自然衰减。
- 时长抗噪（1.0.1）：游戏里的环境底噪、短促音效、背景音乐不再轻易切断时长或拆出碎片——
  - 开新音、判定同键重按都要求**本音频点**像真实按键那样上升并持续（短促音效 130 ms 内就落回原电平；仍在响的余音不会上升；宽带噪音会把所有频点一起抬高、本音并不突出）；
  - 用二次谐波作重按证据时基频必须同向变化（弱谐波一点噪音就能"上升"）；重按沿用该键上一次"刚按下"的电平作参考（原神乐器无力度变化，避免误判后参考被越抬越高）；
  - 已在响的音只由精确音高的峰维持（背景音乐里的半音不会把它"撑"着）；
  - 判"松键/截止"时：趋势线只用电平到顶后的帧拟合；干涉拍频造成的凹陷在 0.35 s 内回升的不算；电平起伏大（与相邻键/背景音乐拍频）时要求更深的跌落；拟合不可靠时要求截止式的急速跌落（快于 100 dB/s）；噪音里的"咔哒"只有与本音跌落区间吻合才用于对齐。
- BPM：和弦合并为一个起音事件 → 一/二/三阶起音间隔在候选周期上做软高斯核打分（按倍数 1/√k 降权，抑制半周期/倍周期）→ 分段同相位网格合并回归精修。
- BPM（1.0.5 改为拍子级）：对候选拍周期 0.27–1.5 s 打分起拍——落在拍点上的起音记 1 分，落在半拍 / 三分 / 四分 / 六分拍上的记 0.5 / 0.35 / 0.35 / 0.2 分，和弦按音数加重，拍点覆盖率低的轻度降分，乘以 120 BPM 为中心的速度先验；之后锁相跟拍：拍上的起音修正相位与周期，细分上的起音不影响速度；每 0.6 s 用最近 7 个起音复查，新拍周期与当前相差 > 8%、得分高 20%、隔 0.8 s 再查仍一致才换；每 2 s 复核拍子层级（半速 / 倍速 / 3:2）。显示值由速度段内拍点的加权回归给出。旧版（1.0.2–1.0.3）显示"最常见的音符间隔"的速度，音符变密时读数会翻倍。
- 谐波误检（1.0.5）：谐律键琴、跃律琴低音区的二次谐波比基频还强，旧规则（谐波弱于基频一半才去掉）把谐波当成了别的键。现按实测音色（`detection.TIMBRES`，分低 / 中 / 高音区）判断：某个峰是正在发声的更低键的整数倍频、且不超过该音区该次谐波的实测电平（单独按下的音的 min(P90, 中位 + 8 dB)，再加 2 dB）就当作谐波。音色与准确率都用游戏录像做真值测得（`python eval_game_video.py 录像.mp4 乐器名 --grid Q键圆心x,y,横向间距,纵向间距 [--old] [--timbre]`：界面上被按下的键会变色，逐帧读出来就是真实按键）。7 段录像的结果：

  已知问题（1.0.6 时）：镜花之琴的基频几乎听不到（能量在 3–6 次谐波），晚风圆号最低的显著分音在键位音高下方一个八度、2–4 次谐波比它强，这两种的音高识别需要另做（1.0.7 已按音色模板改判，见下）；同一个键还在响时又按了一次（重按）仍容易漏。
- 快段落漏检（1.0.6）：逐个对照漏检，主要是"攻击不够骤"（这个频点本来就有余音或邻键泄漏，逐帧比值上不去）和"没有对应的起音峰"（密集处起音函数的背景被抬高，起音峰过不了门限；或别的音同时截止、起音被当成截止）。新增后备判定：这种候选不再直接丢掉，而是在它首次出现前后找这个音高电平骤升的时刻，要求骤升 ≥6 dB、比其它频点的整体抬升高 6 dB、起音后两帧都高于起音前两帧（相邻键拍频不算）、电平不低于这个键"刚按下"的典型电平 4 dB 以上（排除背景音乐里的同音高长音）、不能被更低的键的谐波或附近更响的键的窗函数泄漏解释，且 130 ms 后仍高于起音前；起音时刻对齐到附近的正式起音峰。大和弦（同一起音已认出 ≥4 个音）、只差半音的相邻键正在响、圆号都不用后备判定。游戏录像里，距上一次按键不到 0.2 秒的按键漏检率从 58% 降到 43%（不算镜花之琴、圆号是 56% → 40%）；后备判定救回的真按键约是它多出来的误检的 2.6 倍，总精确率没有下降。另外每帧最多取 16 个峰（原来 12 个）。后备判定开出的起音不参与边界值排查的按键计数（计数结果与 1.0.5 相同）。检测耗时增加约 17%（仍有 4.6 倍实时）。另外，同一个键还在响时又按了一次、电平几乎没回升的重按，会再看基频相位是否在起音处"重置"（游戏重按时重新播放采样）：只在正式起音峰上用，要求起音前后各自是稳态、相位跳 ≥1.6 弧度、电平不低于刚按下时 3 dB 以上，且同一起音没有与它有泄漏关系的新音。
- 按音色模板认键（1.0.7）：镜花之琴的基频几乎听不到（能量在 4–8 次谐波），晚风圆号的二次谐波比基频强，谐律键琴低音区各次谐波与基频相当——按"最强的峰就是基频"认键，常认成高八度、高十二度的键。现在每个音开出来后，取起音后 8–93 ms 的频谱减去起音前的频谱，对"检测到的音高是它的 1–8 次谐波、且这次谐波在模板里不弱于 -20 dB"的各个键，按各次谐波幅度 × 模板权重求和，取最高的键（`detection.KEY_TEMPLATES`；模板 = 录像里前后 0.15 s 没有别的按键的音各次谐波相对最强谐波的中位电平）；同一起音的两个音改判成同一个键时只报一个。用录像前半段学模板、后半段评测（不偷看）：镜花之琴精确率 12% → 56%、召回 11% → 42%，圆号 30% → 47% / 29% → 34%，谐律键琴 76% → 83% / 66% → 68%。风物之诗琴、悠可琴基频本来就最强，跃律琴改判后召回下降，这三种不用。
- 圆号按键时长（1.0.7）：圆号按住期间一直发声，键面也一直变色，录像里能读出真实按住时长。琴类的截止规则（相对趋势线 -6 / -12 dB 的急速跌落）对圆号不适用——它起伏大、松键跌落慢，常被相邻音、颤音误触发，或一直等不到而记成"余音衰减"。现在圆号的松键时刻 = 电平跌出"按住时的平台"：平台趋势线用起音后 60 ms 起的前 30 帧拟合（斜率钳在 -40~0 dB/s，截距取 75% 分位，之后固定），之后第一处连续 8 帧低于平台 8 dB 的跌落，取 -6 dB 交越并按截止陡峭度查表扣除释放尾音。对照录像 91 个音：|误差| 中位 323 → 231 ms、偏差中位 -91 → -43 ms；合成基准里理想的平稳持续音时长 MAE 0.7 → 10.6 ms（回归测试仍在 15 ms 内）。圆号的时长误差仍大，主要是同时按的别的音、背景音乐让"平台"本身起伏。

  圆号按键时长（对照画面按住时长）|误差| 中位 231 → 217 ms（检出的音多了，可对照的从 91 个增到 133 个）。试过但没有用的：同键重按、后备判定、相位重按的各项门限微调（合计 F1 变化 < 0.1）；给跃律琴、风物之诗琴加音色模板（跃律琴召回 54% → 44%）；圆号"平台"规则的各项参数与二次跌落规则（时长误差变化 < 2%）。跃律琴漏检里最多的是同时按下的八度（低音区二次谐波比基频强 13 dB，单独按与和八度同按时 h2/h1 的分布重叠），还没有好办法。
- BPM（1.0.8）：层级复核由每 2 s 改为每 1 s，并且不只看半速 / 倍速 / 3:2，也看最近 8 s 起音重新估计的最佳拍速（要求得分高 5%、且最近 4 s 单独估计指向同一速度，渐变速时不触发）。录像 BPM 逐窗读数与 1.0.7 相同（谐律键琴 21-18 开头 12 s 的快速轮指仍读 102–109：那段 104 / 129 / 158 三个层级的得分只差 0.40 / 0.41 / 0.46，起拍锁在 104 后要等到 25 s 才换到 129，这一处没有解决）；1.0.8 的召回变化本会让 21-18 的逐窗准确率从 73% 降到 68%，这一改动把它拉回 73%。合成变速基准跳变次数 3 → 4（"频繁变速"一例），其余不变。
- 调性（1.0.2 改进）：Krumhansl-Schmuckler 调性轮廓匹配，用最近 20 秒、至少 6 个音；每个音按"占时"（到下一个音的时间）而不是余音长度加权，低音和句尾音（其后有停顿）多加权；原神这几种琴只有白键，候选只在 C 大调 / A 小调之间选（不会报出琴上弹不出来的调）；置信度 = 第一名相对第二名领先多少，分不开时显示"与 X 难分"；新调持续领先 2.5 秒才切换显示。
- 和弦（1.0.2 改进）：只看最近一次同时按下的那组音（之前还在响的余音、之后在和弦上弹的旋律音都不算），分解和弦从最近一个低音累积；单音旋律（低音之上是级进）不报和弦；常见三和弦/七和弦优先，低音是根音加分，显示转位（如 C/E）；敲击产生的相邻频点假音不参与；变化要保持 0.15 秒才切换显示。
- 评测：`python test_detection.py`（合成音频回归测试，带断言）；`python benchmark_timing.py --old`（带真值的时间精度基准，并与 git HEAD 版本对比）；`python benchmark_timing.py --noise --old`（底噪/音效/背景音乐下时长模块的敏感度对比）；`python benchmark_timing.py --tempo --old`（频繁变速时 BPM 多快跟上、稳定速度时是否乱跳）；`python eval_harmony.py`（和弦/调性算法与旧版对比）；`python eval_screening.py`（边界值排查：大和弦计数、长轮指的脚本检出与人手误报、真实录音）。

## 构建与发布

**Windows（exe + 安装程序）**：需要 Python 3.10+ 与 [Inno Setup 6](https://jrsoftware.org/isinfo.php)。

```
python -m pip install -r packaging\requirements-build.txt
powershell -ExecutionPolicy Bypass -File packaging\build_windows.ps1
```

产物在 `dist\`：`原神乐器演奏检测器.exe`（单文件）、`GenshinInstrumentDetector-<版本>-win64-portable.exe`、`GenshinInstrumentDetector-<版本>-win64-setup.exe`。

### 发布前核对

当前源码的 Windows 版本在 `app_version.py` 中，Android 版本在 `android_app/app/build.gradle` 中，两者可能不同。发布包的版本以实际构建结果为准。

现有 GitHub Actions 工作流在推送 `v*` 标签时会同时构建 Windows 和 Android。只发布 Windows 时，应使用单独的发布流程，避免把 Android 包标成 Windows 的版本。请先核对两个平台的版本与附件，再公开 Release。

Windows 构建还会执行以下检查：

- 验证构建环境可以导入 PySide6、pyqtgraph、soundcard 和 numpy。
- 使用 `packaging/verify_windows_bundle.py` 检查成品中的界面模块、Qt 扩展与 Windows 平台插件。
- 让成品 EXE 通过 `--self-test-gui` 创建并渲染主窗口，生成成功报告后才继续打包。

这些启动检查不等同于真实游戏演奏、识别精度或安装过程的验收。
